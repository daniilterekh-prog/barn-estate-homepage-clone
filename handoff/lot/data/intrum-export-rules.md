# Intrum → страница лота: логика выгрузки

27.11.2026. Основание: карточка 601669, таблица полей и пять новых фото экрана от пользователя. Формата выгрузки пока нет — пользователь подтвердил, что сейчас нужна логика. Это контракт для будущей интеграции, не описание подключённого API.

## Главное правило

**Не разбираем описание на блоки и не сочиняем тексты из признаков.** Одно поле «Общее описание» целиком заполняет «О квартире». Остальные блоки — проекции конкретных полей и файлов. Если источника нет, элемент скрывается либо используется предусмотренный запрос материала.

| Блок | Источник Intrum | Правило |
|---|---|---|
| Херо | Название, Цена/Валюта, город/район, Общая площадь, Комнат в квартире, Этаж/Этажей в здании, Ремонт; Фото | Фиксированный шаблон подписи/цифр. Никакого нового рекламного текста. ID — контекст ссылок/обращений. |

## Отбор к публикации

1. Прочитать **«Выгрузки на сайты → Выгрузка на сайт»**. Только явное `Да` разрешает автоматическую публикацию. `Нет` и пустое значение — не разрешают.
2. Проверить статус по согласованному словарю. «Свободная» и «Вид продажи: Свободная» — разные поля. Статус сам по себе не отменяет переключатель выгрузки. Словарь остальных статусов на этих скринах не установлен.
3. Проверить ID, название, город/тип/сделку и доступность собственного основного фото. Невалидный обязательный источник — ошибка подготовки, не заглушка из другого объекта.
4. Выдать только разрешённую публичную модель. Не отправлять всю карточку в браузер и не прятать служебные поля CSS.
5. Если опубликованный объект получил `Нет`/недопустимый статус — снять его с витрины и из похожих, а не просто прекратить обновления старой страницы. URL обрабатывать по принятой политике снятых объектов.

**601669:** на фото 2 стоит «Выгрузка на сайт: Нет». При такой настройке будущая автоматическая выгрузка его не публикует. Действующее демонстрационное превью собрано вручную по поручению пользователя; API и автоматическая публикация не подключены.

## Что не попадает на сайт

Комиссия компании, кадастровый номер, источник «Наша база», рабочие контакты без публичной связи, собственник/его вкладка, лента событий, комментарии, документы из событий, просмотры/оценки/баллы ликвидности, рекламные площадки и режим продвижения для Циан. «Цена для Домклика» не заменяет основную цену.

«Название ЖК/КП (для сортировки)» — кандидат связи/сортировки, не доказательство публичного названия и не текст о доме. Для ссылки на страницу ЖК нужен подтверждённый ID связанного проекта. Карта CRM/«Открыть панораму» не переносится внутренним iframe: передаются только координаты.

## Описание и безопасность формата

Промежуточное публичное поле — `descriptionText` (строка). Источник — полное «Общее описание», не укороченное отображение карточки со ссылкой «подробнее…». Формат API/ID поля пока неизвестны.

Если выгрузка даёт HTML, серверный адаптер удаляет script/style/обработчики/внутренние CRM-ссылки, переводит абзацы, br и списки в текст с переносами и декодирует сущности. Слова не переписывает. В браузере строка вставляется через `textContent`, без `innerHTML` и выполнения CRM-разметки. Скрин 4 полностью перенесён в `description.txt`; это транскрипция пользовательского снимка, не API-ответ.

Свёрнутая колонка вместе с кнопкой не выше фото справа. На узком экране — компактный бюджет восьми строк. Короткий текст не обрезается; кнопки нет. Без JavaScript полный текст доступен. По «Читать далее» раскрывается тот же текст целиком; по «Свернуть» — обратно. Высота пересчитывается после шрифта, загрузки/изменения фото, ширины и текста.

## Нормализация и качество

- Числа хранятся числами; запятая/пробелы нормализуются при чтении. Форматирование м²/₽ выполняет сайт.
- `Да`, `Нет` и отсутствие — три состояния. Отрицательные флаги не превращаются в рекламные преимущества. Оснащение не создаёт отдельный список в «О квартире»; оно уже может быть описано в общем тексте.
- Значения характеристик берутся из своих полей, не извлекаются из описания, не считываются автоматически с изображения плана.
- На скринах кухня = 11 м², потолки = 2,7 м; в описании/плане = 10,66/2,65. Нужна корректировка в CRM перед настоящей выгрузкой. Текущий макет ранее использовал точные значения по плану; это ручная настройка демо, не правило адаптера.
- Комнаты = 2 и спальни = 2 требуют сверки. Не рассчитывать спальни из комнат и не переименовывать помещения по изображённой мебели.
- Любые добавленные вручную данные (экспликация, выбранное фото дома, текст о доме) должны быть явно отмечены как ручное дополнение, не выдаваться за поля Intrum. Если в реальной выгрузке нет роли фото для дома, фото дома автоматически не угадывается; блок остаётся с характеристиками без фотографии.

## Как внедрять после выбора формата

1. Получить пример JSON/XML и ID полей/файлов. Привязать **группу + стабильный ID**, не полагаться на уникальность видимых подписей.
2. Серверный адаптер: отбор → чтение allowlist → нормализация → контроль качества → формирование публичных полей.
3. Отдельно связать сотрудника/ЖК и публичные медиаресурсы. Секреты/рабочую карточку в frontend не передавать.
4. Рендерер использует только публичную модель: `id/title/priceRub/locationLabel/facts/descriptionText/building/location/floorPlan/gallery/broker/related`.
5. Проверить запрещённый/пустой переключатель, снятие с публикации, пустые опциональные поля, Да/Нет/null, невалидную цену/площадь, описание целиком, фото/план и приватные поля. Подключение API — отдельная реализация после появления формата.

Изменения текущего примера: `lot-page.js` (полный текст без преимуществ), `kit/vendor/lot-description.js` (поведение из ЖК), `lot-example-601669.js` (полный источник). Проверка — реальная высота фото/колонки на адаптиве, раскрытие/сворачивание, короткий текст и отсутствие обрезки без JS.
